Cómo y dónde usamos IBM Bob

IBM Bob fue utilizado de forma continua a lo largo de todo el desarrollo del proyecto, desde la concepción de la arquitectura hasta la generación del código de producción. A continuación se detallan los usos específicos:

01
Diseño de arquitectura y decisiones técnicas
Bob guió la decisión de usar un Bridge Java con JTOpen como capa intermedia entre Laravel y Db2 for i, ante la imposibilidad de instalar el driver ODBC de IBM i Access Client Solutions en la laptop de trabajo con restricciones de IT. Bob evaluó las alternativas (ODBC, SSH con phpseclib, JDBC puro) y recomendó la solución viable dado el entorno real del equipo.
IBM Bob
02
Generación del microservicio Bridge Java
Bob generó el microservicio Bridge.java completo: un servidor HTTP puro usando com.sun.net.httpserver.HttpServer (incluido en el JDK, sin dependencias extra), con conexión JDBC via jt400, serializador SQL→JSON propio, manejo de parámetros de query, CORS habilitado y endpoints para objetos, incidentes, cambios, usuarios y salud del sistema. Todo compilable con un solo comando sin Maven ni Gradle.
IBM Bob
03
Backend Laravel completo
Bob generó el IBMiBridgeService.php, el ComparadorController.php con lógica de comparación de objetos entre 3 ambientes, detección de diferencias por timestamp, generación del paquete de pase, y el SystemHealthController.php. También generó el archivo de rutas api.php y las instrucciones de configuración del .env.
IBM Bob
04
Diagnóstico de conectividad y permisos IBM i
Bob guió paso a paso el proceso de verificación de conectividad SSH al LPAR (192.168.250.22), la identificación del problema de permisos con *N *N en RUNSQL, y los comandos CL exactos para otorgar acceso (GRTOBJAUT) a las bibliotecas necesarias. También identificó que qsh -c "db2 '...'" era el método funcional para ejecutar SQL desde bash en ese LPAR específico.
IBM Bob
05
Componentes React del frontend
Bob generó el hook useIBMi.js para consumo de endpoints, los componentes del Sidebar con polling en tiempo real cada 5 segundos al endpoint /api/system-health, y recomendó mejoras al diseño existente: panel de autorización de pase, línea de tiempo de pases y búsqueda global con Ctrl+K.
IBM Bob
06
Documentación y entregables del hackathon
Bob redactó la Declaración del Problema y Solución (≈ 490 palabras), esta declaración de tecnología, y el plan completo del proyecto incluyendo cronograma comprimido, guion de demo de 3 minutos y checklist de entregables. También generó el prompt de diseño visual usado en Figma para crear la identidad "sala de control IBM i" con paleta verde fósforo.

Cómo usamos watsonx.ai
watsonx.ai — Centro de Incidentes (Módulo B)

watsonx.ai es el motor de inteligencia del Centro de Incidentes. Cuando un job falla en producción, la consola extrae el joblog real desde QSYS2.JOBLOG_INFO vía el Bridge Java y lo envía al modelo ibm/granite-13b-instruct-v2 con un prompt estructurado que instruye al modelo a:

(1) Traducir los mensajes técnicos IBM i (MCH, RNX, CPF…) a lenguaje de negocio en español, explicando qué proceso de negocio se vio afectado y por qué. (2) Identificar la causa raíz probable basándose en los message IDs y el contexto del job. (3) Generar tres acciones de remediación clasificadas por nivel de riesgo (bajo, medio, alto), cada una con descripción de impacto operacional.

El resultado se muestra en el panel "Joblog crudo · Traducción a negocio" de la interfaz, lado a lado con el joblog original, permitiendo al administrador entender el incidente y tomar una decisión informada sin necesitar al desarrollador presente.
